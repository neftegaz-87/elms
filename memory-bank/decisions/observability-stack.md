# Решение: ELMS как клиент центрального observability

**Дата:** 2026-11-01  
**Статус:** принято (клиентский контракт; центр ещё не подключён)  
**Область:** только ELMS (app-сервер / compose)

## Что живёт здесь

ELMS **не** владеет центральным Grafana/Loki/Prometheus.  
В этом репозитории фиксируется только обязанность **подключаться к центральному серверу** выбранного стека и **отправлять туда логи** (и позже метрики).

## Контракт ELMS

1. Приложения пишут **структурированный JSON** в stdout/stderr контейнеров.
2. На хосте/в compose ELMS работает тонкий агент (**Vector** или **Grafana Alloy**).
3. Агент пушит логи на **центральный Loki** (endpoint центрального observability-сервера).
4. В `docker/compose.prod.yaml` / `compose.dev.yaml` **не** поднимать Loki/Grafana/Prometheus как SoT хранения.
5. Секреты и URL центра — из env/Vault, не из git.

## Центральный стек (ссылка, не SoT этого репо)

Владелец и развёртывание центра: отдельный observability-проект.  
Стек центра (locked): **Grafana + Loki + Prometheus + Alloy/Vector**; **Tempo** — later. ELK не используется.

Пока отдельный репозиторий центра не заведён — канон стека и топологии ведётся там после создания; здесь достаточно знать: ELMS = ship logs to central Loki.

## AC−

- Нет локального Loki/Grafana «вместо центра» в production SoT ELMS.
- Нет dual path: часть логов только на диск хоста без отправки на центр (после подключения агента).
- Нет silent fallback на «логи только в `docker logs`» как замену центральному хранилищу после cutover.
